# 새 데이터가 들어올 때의 규칙 (D1 + 정적 벡터)

새 자료 종류는 아직 정해지지 않았습니다. 아래는 지금 있는 두 가지 유입(산책로 벡터, D1 맥락 표)을 기준으로 한 규칙입니다.

## 어디에 넣나
| 자료 | 위치 | 이유 |
|---|---|---|
| 코스·횡단보도·신호·경사 등 질의가 필요한 표 | D1 `dongnam-running` | Worker가 읽기 전용으로 조회. 무료 쓰기 한도가 있어 큰 선형은 넣지 않음 |
| 부울경 산책로 같은 큰 선형 | `public/data/trails/` 정적 조각(0.1° 칸) | 버전·해시가 있는 파일로 배포. 커지면 R2 검토 |
| 사용자 계정·즐겨찾기·개인 기록 | 기능이 확정된 뒤 별도 저장소(예: Supabase), 공유 키로만 연결 | D1과 이중쓰기·동기화 없음 |
| 건강 원본 | 기기 안에만 | 서버로 보내지 않음 |

## 들어오는 순서
raw 원본 → 검증·중복 제거·해운대 500 m 등 범위 제한 → 로컬 준비(staging) → 무결성 검사 → **명시적으로** 원격 적용. 어느 단계에서도 실패하면 즉시 멈추고 기존 결과를 유지합니다. 원격 변경과 배포는 사람이 승인한 뒤에만 합니다.

## 산책로 벡터 (이 문서가 다루는 부분)
수집 → 빌드 → 점검 → (승인 후) 배포 순서입니다.

```powershell
node scripts/fetch-trails.mjs           # 수집(이어받기 가능, 이미 받은 칸은 건너뜀)
node scripts/build-trails.mjs --dry-run # 만들어서 검증만. public 은 건드리지 않음
node scripts/build-trails.mjs           # 기대 칸 100% 일 때만 public/data/trails 를 교체
node scripts/check-trails.mjs           # 배포 전 점검(읽기 전용). 통과해야 배포 가능
npm run deploy                         # 위 점검을 먼저 실행하고 통과하면 배포
```

- **커버리지 100%가 기본**입니다. 기대 칸 목록은 `region_boundaries.json`과 수집기(`fetch-trails.mjs`)가 쓰는 규칙(경계와 겹치는 0.1° 칸)으로 계산합니다. 현재 199칸입니다.
- 일부만 모인 상태는 `--allow-partial`을 명시해야 만들어지고, `index.json`에 `partial: true`와 `coverage.missing`(누락 칸 목록)이 남습니다. **부분 산출물은 `check-trails.mjs` 기본 모드가 거부**하므로 배포할 수 없습니다. `check-trails.mjs --allow-partial`은 시험용 점검이며 배포 허용이 아닙니다.
- 빈 칸(길이 없는 바다·평지)은 정상 수집 결과로 칩니다. 깨진 캐시 파일은 `coverage.invalid`로 기록되고 수집된 것으로 세지 않습니다.
- **기존 출력 보호**: 새 출력은 `.wrangler/trail-build/`(public 밖이라 에셋으로 올라가지 않음)에서 만들고 검증한 뒤 같은 디스크에서 폴더 이름만 바꿔 교체합니다. 어느 단계에서든 실패하면 이전 `public/data/trails`는 그대로이거나 자동 복원됩니다. 동시 빌드는 락(`.wrangler/trail-build/lock`)으로 막습니다.
- **manifest(`index.json`)**: `version`(조각 해시들의 해시), 조각별 `sha256`·`bytes`, `inputsSha256`(입력 캐시 해시), `coverage`, `partial`, 통계, 한계 문구. 같은 입력이면 같은 `version`입니다.
- **점검 항목**: manifest↔파일 해시·크기·개수 일치, 조각 JSON 구조, 파일 크기 상한(조각 3 MB, 전체 60 MB), manifest에 없는 파일·하위 폴더(임시·백업 잔여물) 없음, partial 표시 일관성.
- 수집기와 `data/raw/trails_cells/` 캐시는 빌드가 읽기만 합니다. 수집은 빌드와 무관하게 계속할 수 있습니다.

## D1 표 (Codex 담당 도구 `npm run db:apply`)
새 데이터 SQL은 `db/pending/`에 새 버전 파일명으로 둡니다(`db/pending-manual/`은 기존 적용 대상이 아닙니다). 확정된 명령 규칙입니다(세부는 README 참고, README는 Codex가 관리).

- `--local` 또는 `--remote` 중 하나가 **필수**입니다. 생략하면 실행되지 않습니다.
- 기본은 읽기 전용 계획 출력이고, **`--apply`일 때만 쓰기**를 합니다. `--dry-run`은 계획만 보겠다는 명시 옵션입니다.
- `--pending`을 붙여야 `db/pending`의 데이터 파일이 대상에 들어갑니다. `--max-files N`은 **대기 중인 데이터 파일 수만** 제한합니다(행 수·쓰기량 제한이 아닙니다).
- `--baseline-legacy --pending --apply`는 해시 없이 적용되었던 기존 기록에 **현재 파일의 해시만 등록**하고 데이터는 실행하지 않습니다. 과거에 적용된 내용이 지금 파일과 같다는 보증은 아닙니다.
- 예(계획만): `npm run db:apply -- --remote --pending --dry-run` / 예(로컬 적용): `npm run db:apply -- --local --pending --apply --max-files 1`

**`--dry-run`이 알려 주는 것은 파일명·해시·바이트 수·상태까지입니다.** 실제 SQL 행 수, 일일 남은 쓰기량, DB 용량은 자동으로 추정하지 않습니다. 적용 전에 D1 대시보드의 사용량·용량, 원본의 검증된 행 수와 SQL의 삽입·삭제·갱신 대상 행 수, 영향을 받는 인덱스를 별도로 확인합니다. 다중 행 INSERT 한 문장이 여러 행을 쓰므로 SQL 문 개수를 행 수로 세지 않습니다.

## 추가 DB 10만 행 이상이 들어올 때
실패한 시도까지 합치면 최소 10만 행 정도를 예상합니다. 이 규모는 무료 한도에 걸릴 수 있어서 다음을 지킵니다.

**한도(2026-11-27 확인)**: Free 요금제는 하루 쓰기 100,000행이며 인덱스 갱신과 `DELETE`도 쓰기로 계산됩니다([D1 요금·측정 기준](https://developers.cloudflare.com/d1/platform/pricing/)). Free DB 하나당 크기 한도는 500 MB입니다([D1 한도](https://developers.cloudflare.com/d1/platform/limits/)). 이 계정의 실제 Free/Paid 플랜과 일일 사용량은 아직 확인하지 못했습니다.

- **행 수만으로 무료 적재를 보장하지 않습니다.** 10만 행을 한 번에 넣으면 인덱스까지 합쳐 일일 쓰기 한도를 넘을 수 있습니다. 인덱스가 N개인 표는 행당 쓰기가 1 + N 쯤으로 늘 수 있고, 재적재 전의 `DELETE`와 실패 후 재시도도 더해집니다. 일일 사용량을 실제로 재 보지 않은 추정은 한도를 보장하는 근거가 아닙니다.
- **나눠도 하루 총 쓰기는 줄지 않습니다.** SQL을 여러 파일로 쪼개면 중간에 멈추고 이어 가기 쉬울 뿐입니다. 일일 한도는 날짜를 나눠야 지켜집니다.
- **기본 실행은 계획만 보여 줍니다.** `--apply`는 승인한 SQL을 실제로 실행하므로 그 파일의 `DELETE`도 실행합니다. 데이터와 적용 기록은 파일 하나의 배치로 실행하며, 실패하면 그 파일은 롤백합니다. 여러 파일 전체를 하나의 트랜잭션으로 묶지는 않으므로 완료된 파일은 유지되고 다음 실행에서 건너뜁니다. 같은 파일명에 내용이 바뀌면 해시 오류로 멈춥니다.
- **적용 전 사전 확인(수동)**: `--dry-run`은 파일명·해시·바이트·상태만 보여 주므로, 예상 쓰기(행 × (1 + 인덱스 수))·남은 일일 한도·DB 용량(500 MB)은 대시보드와 `SELECT COUNT(*)` 등으로 따로 확인합니다. 한도에 가까우면 날짜를 나눠 적용합니다.
- **큰 선형·타일은 DB 밖**: 산책로 같은 큰 벡터는 위의 정적 벡터 경로를 유지하고 D1에 넣지 않습니다. 10만 행에 이런 선형을 합치지 않습니다.
- **로컬에서 먼저**: 10만 행 규모는 로컬 D1 회귀 테스트(Codex 담당)로 적용·재개·해시 불일치 동작을 확인한 뒤에만 원격을 검토합니다. 로컬 통과는 원격 일일 한도의 보증이 아닙니다.
- **원격 적재는 별도 단계**: 도구와 테스트가 확인되면 그다음에 사용자가 승인한 범위(파일·대상·날짜)에 한해 원격에 적용합니다. 이 문서의 절차나 테스트 통과가 원격 적재 승인을 대신하지 않습니다.

## 새 SQL 버전 만들기와 줄바꿈 규칙
- 새 데이터는 기존 SQL을 덮어쓰지 않고 새 파일로 만듭니다. `build-trail-context.mjs`는 `writePendingSnapshot`으로 `db/pending/<이름>_<시각>_<해시12자리>.sql`을 만듭니다. 시각은 정렬 가능한 16자리 epoch milliseconds이며 시계가 뒤로 가도 직전 버전보다 증가합니다. 최신 파일과 내용이 같으면 그 파일 경로를 재사용하며 파일을 다시 쓰지 않습니다.
- 전체 스냅샷에는 `-- dongnam-snapshot: <그룹명>` 헤더가 붙습니다. 같은 그룹에서는 **최신 파일만 적용 대상**, 이전 미적용 파일은 `superseded`로 건너뜁니다. A→B→A로 원본이 돌아오면 새 A 버전을 만들어, 대기 중이던 B가 나중에 덮어쓰는 일을 막습니다. 일반 증분 SQL에는 이 헤더를 넣지 않습니다. 증분 파일은 순서대로 모두 적용되어야 하기 때문입니다.
- `db/migrations`와 `db/pending`의 SQL은 **LF로 고정**합니다(`.gitattributes`). CRLF가 들어 있으면 도구가 읽기를 거부합니다. Windows와 Linux에서 SHA256이 달라지는 것을 막기 위해서입니다.
- 이미 적용한 파일의 내용이 바뀌면 적용이 멈춥니다. 고치려면 기존 파일을 복구하고 새 버전 파일을 추가하세요.

**`DELETE` 후 전체를 다시 넣는 스냅샷 파일**(예: `trail_context`)은 한 파일이 하루 쓰기 한도(100,000)를 넘으면 `--max-files`로 나눌 수 없습니다. 그 옵션은 파일 수만 제한하고, 파일 하나는 쪼개지 않으며 자동 분할도 없습니다. 이런 경우는 변경분만 넣는 증분 방식, staging 표에 적재한 뒤 전환하는 방식, 유료 플랜, 저장소 재검토 중에서 정합니다.

## 산책로 빌드 도구의 복구
- 빌드가 교체 도중 실패하면 이전 출력으로 자동 복원합니다. 복원까지 실패하면 `.wrangler/trail-build/run-*/backup`을 지우지 않고 오류(`restore_failed`)에 복구 경로를 알려 주므로, 그 폴더를 `public/data/trails`로 옮겨 복구합니다.
- 락 폴더(`.wrangler/trail-build/lock`)에 pid가 없으면 시작 중인 다른 빌드로 보고 거부합니다. 실행 중인 빌드가 없다면 그 폴더를 직접 지웁니다.
- 모르는 옵션은 거부합니다(`--dryrun` 같은 오타로 실제 교체가 일어나지 않음).

## 범위와 한계
- 새 자료 종류와 행 수는 아직 확정되지 않았습니다(최소 10만 행은 추정).
- 쓰기량·용량은 아직 실측하지 않았습니다. 원격 사용량(대시보드 또는 API)을 확인하기 전에는 "무료로 들어간다"고 말하지 않습니다.
- 이번 읽기 전용 확인에서 DB 파일 크기는 3,723,264 bytes, 표는 23개였습니다. 현재 CLI는 인증 오류 7403으로 원격 계획 조회가 막혀 있으며, Claude의 기존 Cloudflare 연결로 크기와 행 수만 확인했습니다. 플랜 조회는 403으로 실패했고 일일 쓰기 사용량도 확인하지 못했습니다.
- 범용 ETL, Supabase 이전, 회원 기능은 이 범위가 아닙니다.

## 하지 않는 것
- 범용 ETL 프레임워크, Supabase 이전·회원 기능.
- 검증 없이 원격 D1을 바꾸거나 배포하는 일.
